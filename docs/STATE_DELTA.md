# 状态增量传输

## 协议与边界

- 客户端在 `hello` 中声明 `stateDelta: 1`。未声明或声明未知版本的客户端仍接收原来的完整 `m.public` / `m.private`，协议主版本不变；新客户端也能接收旧服务器的原消息。
- 声明支持的连接接收 `m.state`。首次发送与重同步为 `{ t: "m.state", kind, seq, full }`；后续为 `{ t: "m.state", kind, seq, base, patch }`。`kind` 只允许 `m.public` 或 `m.private`。
- `seq` 是进程内编码快照的序号，不是每个频道连续递增的计数；连接必须已有与 `base` **相等**的该频道快照。房间内相同快照/基线共用补丁与编码，私人快照不跨玩家共用。
- `patch` 的操作是 `[路径数组, 新值]`（设置）或 `[路径数组]`（删除对象字段）。同长度数组按索引更新，长度或类型变化整体替换该子树；`null`、字段缺失和空数组不同。补丁比完整帧的 UTF-8 字节数更大时发送完整帧。
- 客户端在网络层重建原消息，然后照常派发 `m.public` / `m.private` 和 `*` 事件，界面/模拟不读取传输元数据。补丁采用写时复制，不修改之前派发的状态；接收方应继续将状态视为只读。
- 基线不匹配或补丁非法时，不派发部分状态；合并发起 `state.resync`，暂停应用受影响频道的补丁，直到收到完整状态。该请求使用既有重同步节流和重型请求限流；被拒绝或未恢复时客户端最多每秒安静重试一次。断线清除本地基线和重试定时器，重连全量恢复。
- 基线只在可靠帧成功排入发送队列后推进。保持现有 FIFO、`b.snap` 可丢弃条件和硬背压断开阈值；增量状态本身不能丢弃。结果回放保存的仍是原始全量消息，投递时重新适配当前连接。
- `b.pool`、`b.start`、战斗事件、结算、公告、房间消息均保留原协议，不改变战斗规则，也不改变操作确认时机、公共状态节流或状态发送次数。
- 源码页面的 build 标识包含新的浏览器状态解码模块 `shared/stateDelta.js`；生产构建中它随首屏网络模块打包，仍不引入战斗模拟或渲染器的首屏静态依赖。

这一阶段减少的是**待压缩/发送的正文**，并复用房间公共补丁编码；`privateView()` / `publicView()` 仍完整生成并编码，尚未实现细粒度脏标记、广播压缩正文复用、周期更新错峰或生产多实例路由。新增快照会占用内存，延迟收益不等于内存收益。

## 四人房间传输压测

`tools/bench-state-delta.mjs` 启动独立服务进程，以真实四人房间和 `room.ready` 路由对比 `full` / `delta`。待生成视图为相同模板的变化快照，每房间公共状态单独编码/发送，每玩家私人状态独立发送；不是同一状态广播全部连接。

样本文件由调用者提供，格式为 `{ "public": <完整 m.public>, "private": <完整 m.private> }`。默认路径 `.cache/ws-real-samples.json` 是本机前轮压测的样本，其他机器需准备对应文件，不随源码发行。

```sh
node tools/bench-state-delta.mjs --variant full --samples .cache/ws-real-samples.json --sockets 2500 --seconds 20 --hz 1
node tools/bench-state-delta.mjs --variant delta --samples .cache/ws-real-samples.json --sockets 2500 --seconds 20 --hz 1
```

可使用 `--hz 4` 增大后台频率。可选 `--server-cpus 0,1,2,3,4,5,6,7 --client-cpus 8,9,10,11,12,13,14,15` 固定进程亲和性，需要 Python psutil 和对应处理器；默认不修改亲和性。服务固定四个 libuv 线程、默认 `permessage-deflate` 参数；全量初始同步在预热阶段完成。

`--deflate-threshold 1024` 保持生产默认；`--deflate-threshold 0` 只用于“双方所有消息均压缩”的独立对照，不修改生产配置。新增 `server.wire.state` / `other` 按实际 WS 帧的 RSV1 位分别记录压缩与未压缩正文、帧头及帧数，再与套接字发送字节、客户端接收字节和 zlib 回调交叉校验；因此压缩调用为零不再被误解为实际发送字节为零。该帧观察器依赖当前 ws 8.x 的内部 API，仅存在于压测工具。

CPU 分开输出 user/system/total CPU 时间及对应 wall time。`averageCorePercent = totalMs / wallMs × 100`，100% 是一个逻辑核；`averageAllocatedPercent` 再除以服务进程分配的逻辑核数（本机测试为 8），不是全主机或单独 zlib 的占用。启动、建房、初始全量同步不计入；测量包含收尾排空和测量工具自身的开销。初次全量预热等待发送队列清空；测量结束等待已生成状态到达、发送队列排空，停止新的测试下行消息后再采集一致的字节/CPU 边界，防止周期在线人数消息恰好跨越采样时刻。

每连接每四秒发送 ping 和真实准备操作，操作成功后、`ok` 前通过生产 `sendSession` 发送变化私人状态。`operationStateMs` 从操作发出测到关联状态完成解码/补丁重建，`operationAckMs` 单独记录确认到达；核对关联状态在确认之前，不能以 ping/确认代替状态到达 p95。同时报告生成/接收数、补丁解码失败、超时、正文/实际 WS 字节、压缩调用次数、CPU 和结束时 RSS。

仅使用本机回环、合成变化状态，**不模拟游戏操作成本、战斗、AI、Worker、Redis、TLS、公网、客户端渲染、长时稳态、初始化/重连风暴或完整 Linux 对局负载**。样本变化集中于金币、准备标志和测量字段，不代表购入/合并/阶段切换的大范围变更；此类变更可回退全量。失败场景的 p95 只来自成功样本，应同时检查失败率，不能宣称达标。实际 WS 字节包含房间广播/心跳及帧头，不含 TCP/IP/TLS；RSS 未强制 GC，不能推算容量上限。

发布需同时部署本分支服务器、重新构建的前端并重启；Docker 需要构建新镜像并重建容器，而非仅 restart。保留环境配置、公告与挂载，不承诺跨版本对局恢复。本改动未更改游戏数据/素材，无需因此重新复制数据 CDN。

## 2026-10-09 本机结果

Windows、Node **26.7.0**（不是上一轮的 22.23.2）、服务逻辑处理器 0–7 / 客户端 8–15、单实例四个 libuv 线程。2500 连接 / 625 个四人房间，每轮测量 20 秒；公共后台 1 Hz / 私人后台 0.25 Hz，4 Hz 场景均乘四。常规轮次顺序 full-r1 → delta-r1 → delta-r2 → full-r2，4 Hz 各一轮。先完成初次全量预热，再统计持续更新。

| 场景 | ping p95 ms | 操作状态到达 p95 ms | 后台状态 p95 ms | 接收/生成状态 | 实际 WS 字节 MiB | 结束 RSS MiB | CPU 秒 |
|---|---:|---:|---:|---:|---:|---:|---:|
| full-r1 | 82.25 | 163.88 | 317.23 | 75062/75062 | 92.81 | 848.1 | 13.53 |
| delta-r1 | 109.69 | 16.52 | 0.25 | 75062/75062 | 43.24 | 889.0 | 9.38 |
| delta-r2 | 100.01 | 26.07 | 0.26 | 75062/75062 | 43.12 | 924.4 | 8.56 |
| full-r2 | 65.37 | 122.24 | 243.43 | 75062/75062 | 92.68 | 842.1 | 12.59 |
| full-4hz | 215.01 | 300.13 | 282.73 | 262563/262563 | 245.31 | 884.7 | 30.64 |
| delta-4hz | 212.39 | 116.60 | 0.18 | 262562/262562 | 70.75 | 1216.2 | 15.27 |

这些轮次均无操作超时、顺序错误、补丁解码失败，结束时发送缓冲为零。四轮常规场景各 12562 次操作，后台各 62500 份；4 Hz 操作数相差一次，后台均 250000 份，没有通过丢弃状态减少排队。常规状态正文由约 226 MiB 降至 13 MiB（约 94%），包含其他消息的实际 WS 字节降约 53%；4 Hz 实际 WS 字节降约 71%。

稳态小补丁都低于默认 1024 字节压缩阈值，增量测量期压缩调用为零（**不是禁用压缩**，预热完整状态及较大变化仍按原配置压缩）。这一点解释了状态到达收益，也说明不能外推到所有游戏操作。

**ping 没有改善，RSS 反而上升**：常规结束样本为全量 842–848 MiB / 增量 889–924 MiB，高频为 885 / 1216 MiB。未强制 GC、未做长时稳态或全量重连风暴，不把结束 RSS 当持久内存需求，也不声称内存优化。主要改进是关联状态到达和字节量，不是所有指标均改善。完整状态构建仍未优化，不能直接与上一轮全服合成广播或不同 Node 版本的 p95 对比。

原始结果保存在忽略的 `.cache/state-delta-final-{full,delta}-{r1,r2,4hz}.json`；前轮优化前样本也保留，但以上仅使用最终协议及单调时钟的复测结果。上述数据属于本机传输压测，不是线上容量结论。
